BC DEPLOYMENT ANALYZER — RECORDED PRESENTATION SCRIPT
======================================================
Target length: 8–10 minutes. Screen recording + voice-over.
Format per scene: [SHOW] what is on screen · [SAY] what you say.

------------------------------------------------------------------
SCENE 1 — THE PROBLEM (0:00–1:00)
------------------------------------------------------------------
[SHOW] The customer example document in docs/examples/Nordvik_Industri_AB/README.md,
       or a screenshot of a hand-written implementation document (Word).

[SAY]
I work at a Business Central partner. We build and run customer-specific extensions,
Per-Tenant Extensions, for dozens of customers. Each customer has three to ten GitHub
repositories of AL code and one or more Business Central environments.

The knowledge of what those extensions do lives in the code and in the developers' heads.
Our consultants either read AL or ask around. We write implementation documents by hand,
and they are stale the day after we write them. One real document was missing an entire
feature that existed in the repository. And nobody can quickly say whether the version in
main is actually the version installed in the customer's production environment.

The BC Deployment Analyzer keeps that documentation alive automatically, in Swedish,
and puts it where consultants already ask questions: Microsoft 365 Copilot.


------------------------------------------------------------------
SCENE 2 — WHERE WE STARTED: THE PROTOTYPE (1:00–2:00)
------------------------------------------------------------------
[SHOW] The Git-Knowledge-Connector repo: Scripts/generate_docs.py, scroll to the single
       client.responses.create(...) call. Then the generated Aurora_documentation.md with the
       "KRÄVER MANUELL KOMPLETTERING" placeholders.

[SAY]
This is where I started before the course: three Python scripts. One found repos in GitHub,
one queried Business Central for installed extensions, and one pasted every AL file into a
single OpenAI Responses call and appended whatever came back.

It worked. It produced good Swedish documentation on the first real customer. But look at
what it could not do. It had no idea whether the next run would be as good. There was no
trace of what the model saw. There was no way to measure quality except reading the output.
Every run regenerated everything, so cost scaled with the number of repositories, not with
the number of changes. And for third-party extensions it could only print a placeholder
saying "requires manual completion".

It was a Python script with an LLM call in it. It was not a solution I could govern.


------------------------------------------------------------------
SCENE 3 — THE ARCHITECTURE NOW (2:00–3:30)
------------------------------------------------------------------
[SHOW] docs/diagrams/architecture.png (or the Mermaid diagram in README.md rendered on GitHub).

[SAY]
This is the production architecture. Reading left to right.

A developer merges a pull request in a customer repository. Deterministic Python discovery
inventories the repositories and queries Business Central. That part is intentionally not an
agent: which repos belong to a customer and which version is installed are facts, and facts
should be computed, not generated.

Inside Microsoft Foundry there are two agents. bc-change-tracker reads the pull requests
merged since the last run and produces an impact verdict and a Swedish changelog.
bc-code-analyst reads the AL source through a deterministic analysis tool and writes, or
surgically updates, the documentation for each app.

The output is Markdown committed to GitHub. The Microsoft 365 Copilot GitHub connector
indexes it, so a consultant can ask "how does the minimum order fee work at Nordvik" and get
an answer grounded in the current code.

Around the agents: every run is traced to Application Insights, and an evaluation dataset
scores the agents before each release. Those two boxes are what the course added, and I will
come back to them.


------------------------------------------------------------------
SCENE 4 — DECISION 1: TWO AGENTS, NOT ONE (3:30–4:30)
------------------------------------------------------------------
[SHOW] agents/README.md comparison table, then agents/instructions/change_tracker.md
       (the JSON verdict contract) and agents/instructions/code_analyst.md (the ### / ####
       format rules and "Övriga anpassningar").

[SAY]
Why two agents? Because they answer different questions on different data.

The change tracker works on a small diff: commits, PR titles and bodies, patches. It must be
precise about what changed and honest about how much it matters. Its output is a JSON verdict:
impact none, minor or major, and whether the documentation needs full regeneration.

The code analyst works on a whole repository. It must be complete. Its output is the Swedish
documentation section: one heading per app, one sub-heading per feature, event subscribers
collapsed into "Övriga anpassningar", install codeunits skipped.

Splitting them gives me three things. The orchestrator can skip unchanged repositories for
free with a SHA comparison. The cheap tracker decides whether the expensive analyst runs in
update mode or full mode. And I can evaluate the two jobs separately: verdict accuracy is a
different question from documentation quality. A bonus: the tracker's changelog is the
customer-facing release note.


------------------------------------------------------------------
SCENE 5 — DECISION 2: TOOLS ARE CODE, AGENTS ARE PROSE (4:30–5:30)
------------------------------------------------------------------
[SHOW] common/al_analysis.py: the classify_codeunit function and the archetype comments.
       Then agents/tools.py: the analyze_repo FunctionTool definition.
       Optionally run: python agents/tools.py analyze_repo --org <org> --repo <repo>
       and show the structured JSON (objects_by_type, logic_codeunits, event_subscribers).

[SAY]
The biggest design change from the prototype is what the model is allowed to know.

In the prototype the model read raw AL and decided for itself which files were business
logic, which were event subscribers, and which were install scaffolding. Now that
classification is Python. The analyze_repo tool parses every AL file: object types, fields,
page actions, API properties, event subscriber attributes. It classifies codeunits into the
three archetypes from our documentation standard, detects commented-out code, and hands the
agent a structured JSON plus the source under a size budget.

The agent's job becomes phrasing verified facts in Swedish, not judging code. It cannot
document an object the tool did not find. That is the grounding story, and it is also what
makes quality measurable: a groundedness evaluator can compare the output against the tool
output as context.

Same pattern for the tracker: get_repo_changes uses the GitHub compare API and merged-PR
lookup, filters out pipeline files and translations, and classifies each changed object.
The model reads intent from PR descriptions; it does not invent it.

SCENE 6 — WHAT FOUNDRY GAVE US THAT PYTHON ALONE COULD NOT (5:30–7:30)
------------------------------------------------------------------
[SHOW] Foundry portal, in this order:
       1. Build → Agents: bc-code-analyst and bc-change-tracker listed, with versions.
       2. Open bc-code-analyst → Traces: a run row with tokens, duration, cost; open it and
          show the analyze_repo tool span and the model span.
       3. Monitor tab: agent runs and token charts.
       4. Build → Evaluations: an evaluation run (or evaluation/results/latest.md locally),
          showing coherence, fluency, groundedness, task adherence per case.
       5. Build → Agents → Workflows: bc-documentation-workflow (tracker → analyst).
       If the portal is not available yet, show monitoring/queries.kql, evaluation/README.md
       and orchestration/create_workflow_agent.py instead.

[SAY]
This is the part I want to dwell on, because it is where the course changed the solution
rather than just the code.

The initial idea was a Python-only pipeline. It would have worked, but everything around
governance would have been mine to build: logging, versioning prompts, measuring quality.
The course showed me that Foundry provides those as artefacts, and the structure of the labs,
setup, build, monitor, evaluate, orchestrate, became the structure of my repository.

First, agents as managed, versioned resources. The instructions are Markdown files in git.
Publishing a change creates a new immutable agent version. I can roll back. In the prototype
the prompt was a string in a script.

Second, tracing. One line, AIProjectInstrumentor, and every model call and every tool call is
a span in Application Insights: what the agent saw, what it said, how many tokens, how long.
I added my own spans on top with bc-prefixed attributes: customer, repository, mode, impact,
tokens, duration. So a Kusto query answers "how many tokens did customer X cost last month"
or "which repository is slowest". When a consultant reports a wrong document, I open the trace
and see whether the object was in the tool output. If it was not, the model hallucinated and
I add an evaluation case. If it was, the source was truncated and I raise the budget.
None of that existed in the prototype. I had print statements.

Third, evaluation. Nine cases for a fictional customer, each carrying the exact tool output
the agent would receive, so the run is reproducible without GitHub. Four LLM-judge metrics:
groundedness, task adherence, coherence, fluency. Plus deterministic evaluators for format
and coverage that run free in CI. The gate fails a pull request when a metric drops below
the threshold. Before the course, evaluation was me reading the output.

Fourth, orchestration visible in the portal. The production path is Python, because Foundry
workflows cannot call my local tools yet, but I also register the two agents as a Foundry
Workflow so the collaboration can be tested and traced in the portal.

Fifth, the setup script gives the solution its own resource group, its own model deployment,
its own Application Insights. Cost and access are separated from everything else we run.


------------------------------------------------------------------
SCENE 7 — THE PIPELINE RUNNING (7:30–8:30)
------------------------------------------------------------------
[SHOW] Terminal: python orchestration/run_pipeline.py --dry-run (shows SKIP/UPDATE/FULL per
       repo). Then a real run if credentials are available, showing the tool call lines and
       the run summary. Then open output/<Kund>/README.md and one app document; scroll to
       Ändringshistorik. Finally the BC report <Kund>_bc_Production.md with ✅/⚠️/❓ statuses.

[SAY]
Here is the pipeline. For each active repository it compares the head SHA with the last
documented SHA. Unchanged: skip, zero tokens. Changed: the tracker runs, and its verdict
routes to the analyst in update mode or full mode. The orchestrator assembles the document
itself: header, the agent's section between markers, and the change history with the new
entry on top. Manual notes outside the markers survive regeneration.

The customer index shows every app with the version in Git and the version in each Business
Central environment. The environment report is where the second change from the initial idea
lives: instead of a placeholder for manual completion, discovery now validates versions.
Green means Git and BC match. Amber means Git is ahead, an unpublished change, or BC is ahead,
a build that is not in main. Question marks mean a published app with no repo, or a repo not
installed here. That is a deterministic check, and it catches the upgrade surprises we used
to find by accident.


------------------------------------------------------------------
SCENE 8 — REFLECTION AND CLOSE (8:30–9:30)
------------------------------------------------------------------
[SHOW] SOLUTION_DESIGN.md, the appendix table mapping course concepts to the repository,
       or the "Production readiness in one table" section of README.md.

[SAY]
To reflect on the journey from prototype to production.

The prototype proved the idea: an LLM can write good Swedish documentation from AL code.
The course gave me the structure to make that trustworthy. Specialised agents with tools
moved judgement out of the prompt and into code I can test. Tracing made every run
inspectable and every customer's cost visible. Evaluation datasets turned "it looks fine"
into a number I can gate a release on. Orchestration turned "regenerate everything" into
"document what changed". And Foundry's managed, versioned agents mean the solution is
governed by the platform, not by whoever last edited a Python string.

The most important lesson: treat what the model is allowed to know as an engineering
artefact. Once the tool decides what the facts are, the agent only phrases them, and
phrasing is something you can measure.

Status today: every phase is implemented and verified offline. The first live run against
our Foundry project, GitHub and Business Central is the next operational step, and every
misfire from that run becomes a new evaluation case.

Thank you.
